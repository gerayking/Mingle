# RFC 0001：群聊旁听 V2：在聊时跟得上，不在聊时不打扰

- 状态：已接受（2026-11-20），实现中，见 [实现方案](0001-implementation.md)
- 日期：2026-11-20
- 关联：MING-134 · [V1 博客](../blog/group-hearing-v1.md) · [`spec.md` 4.2](../spec.md) · [PR #168](https://github.com/earayu/Mingle/pull/168)
- 模拟器：[`0001-sim/`](0001-sim/)（`python3 sim4.py 30`，依赖同目录的 `sim2.py`、`sim3.py`）

## 摘要

V1 的旁听只有"被叫到"和"旁听"两种状态。人和 Agent 聊得正热、但没有 @ 它时，话被当成背景闲聊，要等 2 分钟间隔，从人说完到 Agent 开口要 1–2 分钟。

本 RFC 给 V2 定四件事：

1. **节奏按"人"算，不按"群"算。** 每个人有一个参与度 E。只有正在和 Agent 聊的人能推动计时，用他自己的打字节奏判断"说完了"。其他人的话随下一段一起交。
2. **白花的轮数有可以证明的上限。** 每人一个小令牌桶，全群一个大令牌桶。对 owner 只开放一个旋钮：省 / 均衡 / 快。
3. **让人更早看到第一条消息。** 只改提示语：在聊时先说一句再动手，一条消息说一个意思。
4. **对方在补充自己的话时，插进正在跑的那一轮。** 只在这一种情况下插，其他情况照旧合并。

明确不做：急切度参数、Mingle 自动拆段、在线学习权重、按内容判断"是不是在叫它"（先只记日志）。

模拟中，热聊 p90 从约 125 秒降到 60–70 秒，超过 2 分钟的比例从 10–17% 降到 2–4%。没人找它的群，成本和 V1 一样。

## 1. 背景

V1 一段旁听什么时候交出去：

```text
due = max( min(最后一条 + 20s, 开始等 + 60s),  上一段交出 + 2min·退避 )
```

截图里的场景（详见博客）：Agent 刚回完，人接着发了几条，没有 @。这时安静 20 秒、2 分钟间隔、排队、harness 一轮叠在一起，大约 105 秒。

讨论中又暴露出四个问题，V2 必须一起回答：

| # | 问题 | 来源 |
|---|---|---|
| P1 | 一个人连发 N 条、另一个人回 M 条，N 和 M 不对称。按"段"计数（比如"连续 2 段不开口就退出在聊"）会把一阵话切碎，Agent 要么每条都回，要么被踢出在聊 | owner 对第一版 V2 的质疑 |
| P2 | 大群（30–50 人、每分钟 30 条）里，按全群算的安静窗口会被别人的话不断往后推，热聊反而比 V1 慢 | DIYGod `sim2.py` |
| P3 | 一个人就能拖慢全群：每句都带它名字的玩梗者会花光共用的额度；"有人在聊就压住闲聊"会误伤新来找它的人 | Mingle `sim3.py` 反例 |
| P4 | 人感受到的是"多久看到第一条回复"。Poke 这类产品先回一句"行，我试试"再干活，一条一个意思，所以显得快 | owner 和 Poke 的聊天截图 |

## 2. 目标与非目标

**目标**

- 热聊时，从人说完到 Agent 开口：p50 ≤ 50 秒，p90 ≤ 70 秒，超过 2 分钟的 ≤ 5%。剩下的基本是 harness 自己一轮的耗时。
- 群越大、越吵，在聊的人越不该被拖慢。
- 白花的轮数（交出了，Agent 没开口）有写得出公式的上限，一个人不能花光全群的额度。
- 和它无关的群，成本不高于 V1。

**非目标**

- 不改触发路径（@、回复、在它说过话的话题里发言）。
- 不在 Mingle 侧判断"这段该不该回"，那是 Agent 的事。
- 不追求比 harness 一轮更快：投递算法省不掉那 20–45 秒。

## 3. 设计

### 3.1 每个人一个参与度 E

```text
E_i(t) = E_i(t₀) · 2^(−(t − t₀) / 2min)       随时间衰减，每 2 分钟减半

Agent 回了 i                     → E_i = 1，i 的"被晾次数"清零
i 在正文里叫了它的名字或别名     → E_i = max(E_i, 0.8 · 0.5^被晾次数)
交出一段、Agent 没开口           → 这段里每个人 E_i ← 0.6 · E_i
                                   让这段走快速通道的那个人：被晾次数 +1
```

- E 是连续值，不开口只打折、不清零。所以 Agent 安静等对方说完，不会被踢出对话。这回答了 P1：系统里没有"连续 N 段"这种计数。
- 按人算回答了"同时有好几个人和它聊"：每个人走自己的节奏，不会只认一个 peer。
- 被晾减半回答了 P3 的玩梗者：被晾两次后，名字只剩 0.2，低于门槛。

i **在聊**的条件：E_i ≥ 0.25，i 自己的令牌 ≥ 1，并且被晾次数 < 2。

### 3.2 只有在聊的人推动计时

| 谁说话 | 安静窗口 | 最长等待 | 两段间隔 |
|---|---|---|---|
| 在聊的人 i | i 自己的说完时间（见下），按 E 和 V1 的 20 秒插值 | 15 秒到 60 秒，按 E 插值 | 无 |
| 其他人，且有人在聊 | 不推动计时，随下一段一起交；最多压 4 分钟 | — | — |
| 其他人，没人在聊 | V1：20 秒 | V1：60 秒 | V1：2 分钟加退避 |

**i 的说完时间**：记下 i 连续两条消息之间的间隔（30 秒以内的，最近 20 个），说完时间 = `μ + 2σ`，限制在 3–12 秒；不足 3 个样本时用 8 秒。这和 TCP 估算超时重传时间的方法一样。一句话拆成五条发的人，窗口会自己变长。

这回答了 P2：模拟里每分钟 30 条的 50 人群，每次回答花的轮数从 V1 的 7.0 降到 1.9。

### 3.3 两层令牌桶

只有**走了快速通道、交出后 Agent 没开口**的一段才扣令牌。Agent 开口的那一轮本来就值，不扣。

| 桶 | 容量 | 补充速度 | 能不能调 |
|---|---|---|---|
| 每人 | 3 | 每 10 分钟补 1 个 | 写死 |
| 全群 | 见下表 | 见下表 | owner 唯一的旋钮 |

| 档位 | 全群的桶 | 每小时最多白花 | 默认用于 |
|---|---|---|---|
| 省 | 2 个，每 20 分钟补 1 个 | 约 3 轮 | — |
| 均衡 | 4 个，每 10 分钟补 1 个 | 约 6 轮 | 活跃人数多于 5 的群 |
| 快 | 8 个，每 5 分钟补 1 个 | 约 12 轮 | 活跃人数不超过 5 的群 |

**上限。** 在任意一段长 T 的时间里：

```text
快速通道白花的轮数 ≤ min( C_群 + T / r_群 ,  Σ_i (3 + T / 10min) )
```

闲聊的那一路仍然是 V1 的间隔加退避，不扣令牌。所以没人找它的群，成本和 V1 完全一样（模拟中每小时 1.4 轮）。

`--every` / `--mute` 照旧优先，"只能调慢、不能调快"不变：任何档位都不会比 owner 选的更花钱。

### 3.4 一段最多 30 条

- 超过 30 条时，先保留在聊的人说的话，剩下的位置给最新的闲聊。
- `Heard` 第一行写明前面还有多少条没给，以及怎么用 `message read --before` 去取（PR #168 已做）。
- 有人连发多条时，在 `Heard` 里提示："X 连发了 4 条，要回就回一次，不说话没有代价"。用提示语顶住"每条都回"的冲动（P1）。

### 3.5 Agent 正在跑一轮时：只在一种情况下插进去

这一点 DIYGod 和我原来意见不同：DIYGod 主张全部合并、不插话，我主张在聊的人的话直接插进去。本 RFC 的折中：

> **正在跑的这一轮，是在处理 i 的话，而 i 又发了新的一句：插进这一轮。其他情况一律合并，等这一轮结束再交。**

理由：

- **插进去不多花一轮**：这一轮本来就在跑。
- **i 是在补充或纠正自己刚说的话**（"等等，我说的是另一个账号"）。Agent 在动手之前就能看到，不用干完一遍再返工。这是 P4 那种"响应快"真正的来源之一。
- **限定在同一个人**，就不会出现"Agent 对着三个人的话各开一次口"。别人的话照旧合并，不打断它的思路。
- 模拟器里 Agent 不读内容，所以测不出插进去的收益，这也是 DIYGod 测出"无差别"的原因。收益要靠真实日志验证，见第 5 节。
- harness 不支持中途插入时，退回排队。触发路径已经有这套"忙时插入"的机制，可以直接复用。

### 3.6 回复的形态：先说一句，再动手

这一项只改提示语，不改机制。

现在 `manual.md` 里已经有"要花一会儿的事先回一句""写短、写白"，但只对触发路径生效。`Heard` 的提示语只说"有值得说的再开口"。

改动如下：

1. **在聊时交出的 `Heard`** 加一句：

   > You are in a conversation with X here. Reply as you would in chat: a short first line right away if what you'll do takes a moment, then one thought per message. Do not wait to write one long message.

2. **`manual.md` 的回复规则**加一条，适用于私聊和在聊时的群：

   > It is fine to answer in several short messages, one thought each, as the work goes. In a group you are only overhearing, keep it to one.

3. **不做**：

   - Mingle 自动拆段：会拆坏代码块和列表，群里也更吵。
   - 给"短消息"加任何节奏参数。Agent 主动多发几条，在投递算法里本来就是"开口"，不扣令牌。

### 3.7 别名

- `mingle chat alias <chat> add "小跟班"`：Agent 或 owner 登记群里对它的称呼，例如截图里的"bryce小跟班"。
- 别名等同于名字：E 至少为 0.8，被晾减半同样适用。
- 存在 `chats` 上，跟着群走。

### 3.8 内容信号：先只记日志

内容信号指问句里有"你"、紧跟 Agent 上一条发言、没有回复别人等。

模拟中，内容信号把冷启动 p90 从约 130 秒降到约 70 秒，但收益完全取决于误判率：

| 闲聊里被误判为在叫它的比例 | 冷启动 p90 | 白花+插话 / 小时 |
|---|---|---|
| 0（不用内容信号） | 127s | 9.6 |
| 3% | 72s | 14.6 |
| 10% | 112s | 17.7 |

而且在"均衡"档下，误判会花光全群的桶，在聊的人 p90 反而升到 98 秒。中文群里"你……？"在人和人之间很常见，3% 很可能过于乐观。

所以 V2 只记日志：信号命中时，记下"Agent 后来开没开口"。**打开的条件**：样本数 ≥ 200，并且 `P(Agent 开口 | 信号命中)` ≥ 0.5。打开时，还要按群里的消息速率折算：`0.5 × min(1, 6 条/分钟 ÷ 当前速率)`。

## 4. 明确不做的事

| 提议 | 不做的理由 |
|---|---|
| "急切度"：Agent 想插话时不等对方说完 | Agent 只有在一轮正在跑时才可能"想说"。为了看它想不想说而专门开一轮，正是令牌桶要压的那种浪费。人说到一半去打断，在 IM 里也不礼貌。合理的那一半已经由 3.5 覆盖 |
| "连续 N 段不开口就退出在聊" | 段是我们自己切出来的单位，N 对 M 不对称时会出错（P1）。改用连续衰减的 E |
| 全群一个安静窗口 | 大群里会被闲聊不断往后推（P2） |
| 用 Beta 分布在线学习信号权重 | 模拟中更差：在聊的人的信号也一起被打折，衰减回先验后又要重新试错 |
| 两人交叉聊时，截止时间取最晚说完的那个人 | 模拟中没有可测的效果：15 秒的最长等待已经封住了 |
| 按人数自动调多个参数 | 参数扫描显示，说完时间的 kσ、上限、最长等待对 p50 几乎没影响（49–52 秒），写死即可。只有令牌桶是成本旋钮 |

## 5. 指标与验收

PR #168 已经在每段那一轮结束时写一行本机日志：第一条、最后一条、交出、这一轮开始、它第一次开口。V2 补两项：

- **它最后一次开口**（这一轮里）：配合"多条短消息"，区分"第一条来得早"和"说完了"。
- **触发路径也记"第一条消息"的时间**：先回一句的提示有没有用，两条路径一起看。

| 指标 | 目标 | 用来判断 |
|---|---|---|
| 热聊：最后一条 → 它第一次开口，p50 / p90 | ≤ 50s / ≤ 70s | 3.1–3.3 是否达成 |
| 超过 2 分钟的比例 | ≤ 5% | 同上 |
| 交出 → 第一条消息，p50 | ≤ 15s | 3.6 的提示语是否有用 |
| 每小时白花轮数，按群、按档位 | 不超过档位上限，无人群 ≈ V1 | 3.3 |
| 插入后 10 秒内对同一人连发两条完整回复的比例 | 只看趋势，不能明显上升 | 3.5 有没有引出"每条都回" |
| 信号命中的精确率 | ≥ 0.5 才打开 | 3.8 |

模拟结果（30 个种子，`0001-sim/result4.txt`），V3f 即本 RFC 的 3.1–3.4：

| 场景 | V1 p90 | V3f p90 | V1 超过 2 分钟 | V3f 超过 2 分钟 | V3f 白花 / 小时 |
|---|---|---|---|---|---|
| 1 对 1，停顿很长 | 120s | 61s | 10% | 3% | 2.3 |
| 30 人群，每分钟 6 条 | 125s | 68s | 14% | 4% | 9.6 |
| 50 人群，每分钟 30 条刷屏 | 98s | 59s | 0% | 0% | 12.5 |
| 12 人群，3 人同时在聊 | 124s | 66s | 13% | 2% | 11.9 |
| 12 人群，有人玩梗刷名字 | 127s | 64s | 17% | 3% | 10.4 |
| 2 人交叉聊，打字慢，有闲聊 | 125s | 72s | 14% | 3% | 14.8 |
| 40 人群，24 小时无人找它 | — | — | — | — | 1.4（同 V1） |

模拟的局限：Agent 是否开口按概率决定，不读内容；harness 一轮在 20–45 秒之间均匀取。所以只能比较算法之间的相对好坏，3.5、3.6 的收益只能看真实日志。

## 7. 未决问题

1. **活跃人数怎么算？** 建议：过去 7 天在群里说过话的不同的人。新群没有数据时，按"快"档。
2. **E、令牌、被晾次数都在内存里，重启清零。** 和 V1 的退避计数一样，重启只会让它晚一点，不会丢消息。要不要落库？建议先不落库。
3. **3.5 的"正在处理 i 的话"怎么判定？** 建议：这一轮的输入里包含 i 的消息（触发或旁听都算）。轮里有多个人时，这几个人都算。
4. **档位放在哪？** 建议放在控制台群设置的"听群里所有的话"下面，选项只有三个，不显示数字。
